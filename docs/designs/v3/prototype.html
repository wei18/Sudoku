01設計主張與依據等級

每條主張標三種等級之一,讓 owner 分辨「Apple 規定的」與「我們決定的」。

官方

Apple 文件逐字支持,附出處。本案有:成就呈現格式 · GC 術語 · 回饋動畫 · 觸覺 · 玻璃的層歸屬與用量 · IC 變體要求。

常見做法

業界普遍如此但查無官方規範,二手來源。本案有:進場儀式轉場 · 載入的遊戲化過場。

我方推論

核心主張「盤面即主角」屬於這一類。我們讀完了官方 Designing for Games 專章,它不含畫面結構 / 首頁 / 轉場 / 盤面 / 進度陳列的任何指引。

最重要的一次認知修正

3.0 不是「加玻璃」也不是「拿掉玻璃」,是把玻璃從內容層搬到功能層

現行出貨程式碼已經有 6 處 .glassEffect 套在內容層卡片上 —— HomeScreen.swift:295(共用 ModeCard)· DailyHubView.swift:278 · PracticeHubView.swift:74,153 · MinesweeperDailyHubView.swift:208 · MinesweeperPracticeHubView.swift:91,141。

Don't use Liquid Glass in the content layer.~/.claude/skills/hig/materials.md:28

所以 D-5(卡片不用玻璃)不是設計偏好,是修一個既存的 HIG 違規。這也精準回答 owner 的「要採用 iOS 26 Liquid Glass」:我們已經用了,只是用錯地方。

遊戲感從哪裡來 —— 在不放棄 calm 品牌的前提下

沒有官方證據顯示低彩度與遊戲感互斥。官方三個遊戲感訊號(collectible card、succinct animation、consistent haptics)全部可在低彩度下做到。病灶不是彩度,把品牌糖果化是錯的解法。

#病灶依據等級
1全 App 看不見盤面我方推論
2進度做成統計數字堆疊而非視覺陳列官方
3動作回饋沒有簡短精準的因果動畫官方
4進入遊戲沒有儀式常見做法
參照對象是 Apple Fitness 的獎章與 Photos 的回憶,不是糖果色手遊 —— 兩者都是低彩度系統原生調性,靠「把成果做成可收藏可回看的東西」建立儀式感。calm 的顏色 + 收藏品的骨架。

G6 的明示例外:自訂玻璃面板,因它必須在 sheet 不可用的脈絡中渲染

官方對 sheet 的描述幾乎就是我們 completion 面板的設計(自動玻璃、增大圓角、half sheet peek-through),改系統 sheet 可再省一片自訂玻璃。但裁定維持盤內 overlay。

理由:completion 有 4 條 production 路徑共用同一個 scaffold,其中 pushed review route 在 macOS / iPad 是 detail 欄 push;系統 sheet 在該脈絡是錯的呈現(macOS sheet = 視窗置中 modal,回顧畫面不該是 modal)。overlay 是唯一能讓 4 條路徑跨三平台一致的機制。

代價:多一片自訂玻璃,以退場規則約束。

退場規則

同一畫面同一時間,只有一個自訂玻璃「場景」可見

Check for crowding or overlapping of controls. …avoid overcrowding or layering Liquid Glass elements on top of each other.Adopting Liquid Glass
  • completion 面板出現 → G4 必須先退場(不是被蓋住,是真的 unmount 或去玻璃化)
  • pause overlay 是 ultraThinMaterial(standard material,非 Liquid Glass),不構成疊層 —— 但 G4 在 pause 期間本來就該隱藏
  • 這條抓到 v3.2 的一個實際違規,已修正
  • 措辭更正:G4 依官方「don't mix text and icons across items that share a background」拆成兩個 group(數字鍵 / 工具鍵),所以「最多一片」會自打臉 —— 約束單位是場景:board 的 G4(同屬一個 GlassEffectContainer)與 completion 的 G6 不得同時存在

官方 容器 · 間距 · 圓角

Combine custom Liquid Glass effects to improve rendering performance. …make sure to combine them using a [GlassEffectContainer]Adopting Liquid Glass
  • G4 = GlassEffectContainer(SwiftUI,26.0+)
  • ⚠️ 前一版把用法寫反了,已更正。官方:「Each view with a Liquid Glass effect contributes a shape rendered with the effect to a set of shapes… Configure how shapes interact by customizing the default spacing value of the container」—— 容器靠子視圖各自的 .glassEffect 來合併;「容器內不套」做出來的是空容器
  • 正確寫法:容器內按鈕各自套 .glassEffect,或用 .buttonStyle(.glass)。官方那句「Instead of creating buttons with custom Liquid Glass effects…」的本意是不要自己手刻玻璃外觀,不是「不要套 glass 修飾符」
  • 容器的 spacing 參數控制形狀何時開始融合 —— 部分回答 U-2(官方確有 spacing 語意,是融合距離而非內距)
  • 不覆寫標準間距:「Prefer to use standard spacing metrics instead of overriding them」→ 叢集內距引用系統標準,不寫死數值
  • 分組原則用官方的:功能相似 / 影響同一區域,且跨平台一致 → 輸入組(數字鍵 / 模式)與編輯組(undo / redo / 鉛筆)
  • G4 拆成兩個 group:官方同段「don't mix text and icons across items that share a background」—— 數字鍵(文字)與工具鍵(圖示)不能共用同一背景
  • 【官方】每個圖示按鈕必須有 accessibility label:「Provide an accessibility label for every icon.」
  • 圓角同心【官方】;但「內圓角 = 外圓角 − 內距」這條公式是【我方推論】,官方沒給公式
  • 官方沒給「一組最多幾項」的數字 → 不自訂上限

變體與著色

一律 regular,不用 clear。clear 的適用對象明文是「media backgrounds — such as photos and videos」;盤面是高對比線稿與文字,不是 media。而我們的叢集全都含大量文字,正是官方點名該用 regular 的情況。連帶好處:35% dimming 層不需要。

對象著色規則
玻璃表面本身一律不著色 —— 取背後內容的顏色
狀態指示可著色:MS Reveal/Flag 選取態、Sudoku 鉛筆開啟態
主要動作可著色:G6 的主 CTA
同一片玻璃最多一個著色控制項
官方「To emphasize primary actions, apply color to the background rather than to symbols or text… Refrain from adding color to the background of multiple controls.」

IC 的一般性結論

提高對比下限會壓縮 ramp —— 多階 ramp 必須整體重排

逐階推的後果:identity.tier1 相鄰間距從 1.58:1 崩到 1.15:1;thumbnail 兩階崩到 1.06:1(幾乎無法區分)。

修法:重設整條 ramp 目標 —— identity 4.7 / 7.6 / 12.3、thumbnail 4.7 / 8.6。重排後兩 app、明暗四組全部 rung PASS 且相鄰間距 1.61–1.84。

D-3.1 已裁定:接受 IC 下難度色退化為純明度階 —— pip 數量冗餘編碼仍有效,與 WCAG 1.4.1 相容性反而更好。

工程成本要誠實說

這不是「加個變體」,是把全部 token 遷移到 Asset Catalog

repo 目前一個 Asset Catalog color set 都沒有,token 全是程式碼 hex 常數(ThemeColor struct);colorSchemeContrast / accessibilityReduceTransparency / accessibilityDifferentiateWithoutColor 全部零命中。

官方 Asset Catalog 支援 Appearances + 獨立 High Contrast 勾選,交叉 6 色井;官方明講單純換色就交給 Asset Catalog,不要在程式碼判斷 —— 所以不寫程式碼分支備案。

影響:兩 app 全部 token · ThemeColor 型別 · 既有快照基準(可能整批 churn)· theme 注入路徑。建議與 UI 重構分開排期。

明示裁定 D-3.2 IC 只動前景,不動 surface

規則:Increased Contrast 變體只調整前景(文字 / 填色 / 描邊),不調整 surface。
理由:surface 已是近白與近黑,再推空間極小;而改動 surface 會讓每一個既有配對的對比幾何全部位移,等於重算整份 token。只動前景可達同等辨識度提升,改動半徑小一個數量級。
適用範圍:兩 app 全部 IC 變體。日後若出現「IC 下必須改 surface」的個案,須單獨裁定並記錄,不得作為通則援引。

⚠️ 既有 drift:兩 app 的 status.warning 值不同(#A86A0E vs #D9822B),依「功能色不可覆寫」原則應統一,但超出 3.0 範圍。另 MS 的 #D9822B light 只有 2.70:1,連預設集門檻都不過 —— 使用位置未查清,本文不宣稱它是 bug(U-11)。
